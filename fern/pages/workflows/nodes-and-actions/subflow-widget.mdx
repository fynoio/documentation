The **Subflow** feature introduces reusable and loop-based execution within workflows. Instead of restricting workflows to linear execution, Subflows allow workflows to dynamically redirect execution to another node within the same workflow while preserving workflow context and execution state.

![](/images/subflow-inrtroduction.png)

## Benefits of Subflows

<CardGroup cols={2}>
  <Card title="Bundle repeated nodes" icon="box">
    Bundle repeated workflow nodes into reusable execution units, and reuse common logic without duplicating workflow branches.
  </Card>
  <Card title="Redirect execution" icon="arrow-turn-up">
    Redirect workflow execution dynamically to another node in the same workflow.
  </Card>
  <Card title="Repeat until done" icon="rotate">
    Repeat sections of workflows until conditions are met.
  </Card>
  <Card title="Keep state" icon="database">
    Maintain workflow variables, counters, API responses, and execution state across iterations.
  </Card>
</CardGroup>

This allows workflows to behave dynamically instead of following rigid sequential execution paths.

Subflows are especially useful for:

- Authentication recovery
- Retry handling
- Polling workflows
- Conversational journeys
- Bulk operations
- Reusable API orchestration

## Example

Say a customer asks to block all their cards, and the number of cards is only known when the workflow runs. One **Block card** step inside a Subflow loops once per card, keeps count, and the user is notified once at the end.

## Creating and Configuring a Subflow

Here is a subflow being named in the Subflow editor.

![Naming a subflow](/images/subflow-setup.gif)

<Steps>
  <Step title="Open the Workflow Builder">
    Navigate to the **Workflow Builder** where reusable or loop-based execution is required.
  </Step>
  <Step title="Add the Subflow widget">
    Add the **Subflow** widget from the workflow builder sidebar.
  </Step>
  <Step title="Create the subflow">
    Click **CREATE SUBFLOW** to open the Subflow editor window.

    ![](/images/subflow-configuration.png)
  </Step>
  <Step title="Name it">
    In **Subflow name**, provide a unique and descriptive name, for example `Authentication Retry Flow`.
  </Step>
  <Step title="Add the nodes">
    Build the reusable subflow by adding workflow nodes after **Start**, such as API calls, conditions, wait steps, notifications, variable updates and authentication handlers.

    ```text
    Call API → Condition → Wait → Notification
    ```
  </Step>
  <Step title="Add a Loop or Redirect">
    Add a **Loop** or **Redirect** node wherever the workflow execution should repeat, and configure:

    - Continue conditions
    - Retry conditions
    - Exit behavior
    - Target node for redirection

    This allows the workflow to dynamically jump back to earlier nodes while preserving workflow state.
  </Step>
  <Step title="Set the loop count">
    | Type | Description |
    | --- | --- |
    | **Static Value** | Fixed number defined manually. |
    | **Dynamic Value** | Value determined during runtime using workflow variables or node outputs. |

    <Note>
    The maximum supported loop count is **20**.
    </Note>
  </Step>
  <Step title="Define the fallback">
    Define what happens when retry limits are exceeded, conditions fail, APIs continue failing, or loop conditions are no longer satisfied. For example: exit the workflow, send a notification, trigger an alternate flow, or log a failure event.

    ![](/images/subflow-notification-event.png)
  </Step>
  <Step title="Store the payload (optional)">
    Optionally store payload data returned from the subflow. The payload is stored in JSON format and can later be accessed using workflow variables.
  </Step>
  <Step title="Save">
    Click **DONE** to save the subflow configuration. The reusable subflow is now available within the workflow. To remove it, click **DELETE**.
  </Step>
</Steps>

<Tip>
To update the subflow later, click the Subflow widget and select the **Edit** icon. You can insert the saved subflow wherever reusable execution logic is required within the workflow.
</Tip>

## Use Cases

<Tabs>
  <Tab title="Authentication refresh and retry">
    Long-running workflows often depend on authentication tokens for downstream API execution. During workflows involving waits, retries, or asynchronous processing, tokens may expire before the next API call executes. Without a recovery mechanism, downstream APIs may fail and interrupt customer journeys.

    ![](/images/authentication-refresh-flow.png)

    **Using Subflows:**

    <Steps>
      <Step>The workflow validates whether the authentication token is still active.</Step>
      <Step>If expired, execution redirects back to the authentication node.</Step>
      <Step>The workflow generates and validates a fresh OTP.</Step>
      <Step>The access token is refreshed.</Step>
      <Step>Workflow execution resumes from the original flow path.</Step>
    </Steps>

    The same reusable flow can also handle OTP retries by redirecting execution back to the authentication step until retry limits are reached.

    **Benefits:** eliminates duplicated authentication branches, improves workflow reliability, simplifies retry management, and preserves execution context during retries.
  </Tab>
  <Tab title="Bulk card blocking">
    Enterprise workflows often process dynamic lists where the number of records is unknown during workflow design, such as bulk card blocking in banking workflows.

    Without looping support:

    - API nodes are duplicated multiple times.
    - Separate workflows are created for different record counts.
    - Maintenance becomes difficult.

    ![](/images/bulk-card-blocking-flow.png)

    **Using Subflows:**

    <Steps>
      <Step>The workflow initializes a counter.</Step>
      <Step>It processes the current card using the block-card API.</Step>
      <Step>It checks whether more cards remain.</Step>
      <Step>If more cards exist, execution redirects back to the block-card node.</Step>
      <Step>Failures are retried automatically until retry limits are reached.</Step>
    </Steps>

    This enables a single workflow structure to process any number of cards dynamically.

    **Benefits:** eliminates duplicated workflow branches, supports scalable bulk operations, simplifies workflow maintenance, and improves retry handling for failed operations.
  </Tab>
</Tabs>

## Outcome

The **Subflow** feature enables workflows to become significantly more dynamic, scalable, and maintainable. By supporting reusable execution paths, looping behavior, retry handling, and workflow redirection, builders can create workflows that adapt to real-time conditions instead of relying on rigid sequential execution.
