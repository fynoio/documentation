Workflows let you create an automated omnichannel notification experience for your users using a visual workflow builder.

This feature has the flexibility to connect to any third party tool like Mixpanel, Amplitude, MoEngage, Segment or to any web hooks and use conditional blocks to decide who should receive what notifications. You can also design a pre-defined chat workflow where you can send notifications based on user reply. All these can be achieved with ZERO code.

## What is a Workflow?

Workflows in Fyno is a notifications orchestration service that allows anyone to easily design intelligent notification flows without coding.

Workflow can be used to:

- Deliver notifications based on notification events created from data sources like Segment, Mixpanel, Amplitude or any webhooks.
- Deliver notifications based on a user response to a SMS or WhatsApp notification.
- Design a transactional journey flow based on Notification event trigger.
- Call any APIs and use the response to decide any conditional flow.
- Send Delivery reports back to your backend system or third party analytics tools like Mixpanel through callbacks.

### Workflow as a Transformation Layer

Migrating to Fyno from your current service provider requires no modifications to your existing payload structure. Our workflow is designed to accept any payload format and provides flexible transformation capabilities to match your specific requirements. This migration can be completed without any technical development work on your end.

**Key benefits**:

- Maintain your current payload structure.
- Utilize built-in transformation tools.
- Complete migration without coding requirements.
- Preserve existing integrations and data formats.

## Core Concept

To effectively use workflows, it is important to understand the core building blocks that define how they function.

### Triggers

A trigger is the entry point of a workflow that starts execution and passes data into it. Every workflow must have exactly one trigger; without it, the workflow cannot run.

Triggers determine:

- When the workflow is activated.
- What data is passed into the workflow.
- How the workflow connects to internal or external systems.

Different trigger types are designed for different use cases. Some are event-driven, some are based on user behavior, and others rely on external integrations. Choosing the right trigger ensures that workflows run at the appropriate time, receive the required data, and scale effectively.

We support the following trigger types in workflows:

![](/images/all-workflow-widgets.png)

| Trigger | What it does |
|---------|--------------|
| [Meta Flow](./workflow-using-meta) | Allows workflows to start based on user interactions within Meta platforms such as WhatsApp flows. |
| [Webhook](./workflow-webhook-trigger-setup) | Allows workflows to be initiated through real-time API calls from external systems. |
| [Virtual No](./creating-a-workflow-with-incoming-message-trigger) | A virtual mobile number with the capability to receive incoming messages can be configured here. If you want to design a workflow based on user's response in WhatsApp or SMS, then this trigger should be used. Contact [support@fyno.io](mailto:support@fyno.io) for configuring a virtual number. |
| [Mixpanel](./workflow-using-mixpanel-cohort) | Create the Workflow using a mixpanel cohort as the trigger. |
| [Moengage](./workflow-using-moengage) | Enables workflows to start based on events and user activity tracked in MoEngage. |
| [Notification Event](./workflow-notification-event-trigger) | Allows workflows to start based on the lifecycle of a notification. |

#### How to Choose the Right Trigger

Selecting the correct trigger depends on your use case, data source, and desired behavior.

Use the following guidelines to decide:

- If your workflow needs to start based on backend or system events, use the Webhook trigger.
- If your workflow depends on user behavior tracked in analytics tools, use Mixpanel or MoEngage.
- If your workflow is part of a conversational or interactive flow, use Meta Flow or Virtual Number.
- If your workflow depends on notification delivery or engagement status, use Notification Events.

### Actions

Actions represent the actual operations performed within a workflow.

These are the steps where something happens as a result of the trigger and logic defined in the workflow.

**Examples of actions include**:

- Sending notifications (SMS, Email, Push, WhatsApp).
- Calling external APIs via webhooks.
- Updating user data or attributes.
- Triggering downstream systems.

Actions are executed in sequence unless modified by conditions. They are responsible for delivering value to the end user or interacting with other systems.

### Conditions

Conditions allow you to introduce decision-making into your workflow.

They evaluate data and determine which path the workflow should take next. This enables you to create different experiences for different users based on their attributes or behavior. Conditions typically follow an if/else structure.

Examples:

- If a user is a premium customer, send a premium offer; otherwise, send a standard offer.
- If payment fails due to insufficient balance, retry later; otherwise, notify the user immediately.

Conditions make workflows dynamic and personalized, ensuring that users receive relevant communication instead of generic messages.

## How Workflows Work

The best way to explain the full scope and capability of Workflows is with an example. So, let's dive right in.

Company ABC handles payments on its website via an external payment gateway.

The requirement is:

- To send a notification to the customer whenever an online payment succeeds or fails.
- If a payment fails, the Workflow should handle the failure scenario differently depending on the type of customer.
- If the user is a Power User, then convert the payment type to COD and confirm the order by sending an Email and SMS.
- If the user is non-Power User, then send a SMS with a payment link to retry payment.

Fyno's Workflow makes it simple to operate this end-to-end process.

While Fyno's notification events will handle the delivery of notifications, the true power of Workflows can be harnessed by calling any APIs as part of the Workflow and creating actions based on the response.

For this example, let's assume that company ABC has two API endpoints:

- `/customers`: a `GET` endpoint that returns the type of customer.
- `/orders/{{customer_id}}`: a `PUT` endpoint that can update the customer's order details.

Here is how the end-to-end process would work. The animation follows each customer through the workflow, one path at a time.

![](/images/workflow-payment-example.gif)

### Setup

<Steps>
  <Step title="Create the workflow">
    Company ABC creates the Workflow in Fyno.
  </Step>
  <Step title="Connect the payment gateway">
    ABC then adds the Workflow URL as a webhook for successful and failed payments on the payment gateway site.
  </Step>
</Steps>

### What happens for each customer

<Tabs>
  <Tab title="Customer 1: payment succeeds">
    Customer 1 makes a successful purchase on ABC's website.

    The Workflow fires, and the customer receives an SMS and email confirming the successful purchase.
  </Tab>
  <Tab title="Customer 2: Power User">
    Customer 2 cannot make a successful online payment due to an issue with the bank. The Workflow fires and, due to the failed payment, calls the `/customers` endpoint to get the customer type.

    1. Customer 2 is found to be a Power User (best user cohort in terms of monetisation).
    2. The order is confirmed despite the failed payment, and the Workflow converts the order type to COD by calling `/orders/{{ customer_id }}`.
    3. If this API call is successful, the Workflow sends an order confirmation via Email and SMS.

    <Note>
    If the call does not return a `200` response, the Workflow sends the retry communication with a payment link instead.
    </Note>
  </Tab>
  <Tab title="Customer 3: not a Power User">
    Customer 3 cannot make a successful online payment due to an issue with the bank. The Workflow fires and calls the `/customers` endpoint to get the customer type.

    1. Customer 3 is found to be a non-Power User.
    2. The Workflow sends a notification with a payment link to retry the payment.
    3. Once Customer 3 successfully makes the payment, they receive the Order Confirmation communication.
  </Tab>
</Tabs>

What would have otherwise required more than a few lines of code to configure, is being addressed with Fyno's Workflow feature, allowing you to add triggers, provide conditions and decide outcomes, all with a visual understanding of how the entire flow will work.

## Create a Workflow

Here is the full flow at a glance, from creating a workflow to taking it live.

![](/images/workflow-create.gif)

<Steps>
  <Step title="Open Workflows">
    In the side menu, go to **Workflows** under **ADVANCED**. The page lists all your workflows. You can search by name, filter by **Version**, switch the layout, and filter by group from the panel on the left.

    Click **CREATE**.

    ![](/images/workflow-list.png)
  </Step>
  <Step title="Name the workflow">
    In the **Create Workflow** window, fill in:

    - **Name**: a name that tells your team what the workflow does.
    - **Add To Group (Optional)**: puts the workflow in a group so it is easier to find later.
    - **Description (Optional)**: a short note on what the workflow is for.

    Click **SUBMIT**.

    ![](/images/workflow-create-modal.png)
  </Step>
  <Step title="Pick a trigger">
    The workflow builder opens with all the trigger types around the centre. Click the one that should start your workflow. See [Triggers](#triggers) to decide which one fits.

    ![](/images/workflow-trigger-picker.png)
  </Step>
  <Step title="Build the flow">
    Add nodes from the panel on the left of the canvas and connect them to set the order of steps, such as sending a notification event or waiting for a set time before the next step.

    Click **SAVE** to save your changes to the **Test** version.

    ![](/images/workflow-builder.png)
  </Step>
  <Step title="Go live">
    When you have tested the workflow, click **GO LIVE**, then click **CONFIRM**. See the **Go Live** tab under [Manage Workflows](#manage-workflows) for more.
  </Step>
</Steps>

## The Workflow Builder

The top of the builder shows the workflow name and its version, along with the controls you use most.

![](/images/workflow-builder-header.png)

| Control | What it does |
|---------|--------------|
| **Version dropdown** | Shows the version you are viewing, for example `v1 (Test)` or `v4 (Live)`. Use it to switch between versions. |
| **Created / Updated** | Shows who last changed the workflow, which version, and how long ago. |
| **History icon** | Opens the change logs. See the **Change logs** tab under [Access and Settings](#access-and-settings). |
| **Customize Token icon** | Opens **Update Workflow Token**. See [Access and Settings](#access-and-settings). |
| **Workflow URL icon** | Opens the **Workflow URL** window. See [Access and Settings](#access-and-settings). |
| **GO LIVE** | Publishes the current **Test** version to **Live**. |
| **SAVE** | Saves your changes to the **Test** version. |

The bottom left of the canvas has tools to zoom in, zoom out, fit the whole flow on screen, go full screen and show a mini map.

## Workflow Options Menu

Each workflow in the workflow list includes a **More Options** menu (**⋮**), which provides access to the most common workflow management actions. These actions allow you to update workflow information, review configuration details, create copies, request deletion, or publish changes without leaving the workflow list.

![](/images/workflow-options-menu.png)

### Available Options

| Option | Description |
|---------|-------------|
| **Edit** | Update the workflow name or change its assigned group. |
| **Copy to another workspace** | Copy the workflow to a different workspace. |
| **View Details** | View the workflow, dependencies, versions, and where it is used across the workspace. |
| **Duplicate** | Create a copy of the workflow. |
| **Workflow URL** | Get the URL used to call the workflow and set who can call it. |
| **Customize Token** | Set your own token for calling the workflow with token authentication. |
| **Delete** | Delete the workflow. |
| **Go Live** | Publish the current **Test** version of the workflow to the **Live** environment. |

## Manage Workflows

<Tabs>
  <Tab title="Edit">
    The **Edit** action allows you to modify the workflow's basic information without affecting its configuration. This is typically used to rename a workflow or reorganize it into a different group.
  </Tab>
  <Tab title="Delete">
    The **Delete** action removes the workflow.

    Before deleting the workflow, the system displays any resources that reference it, helping you understand the impact of the deletion.

    <Note>
    If approval requests are enabled, the deletion is submitted as an [approval request](/approval-request) instead of being deleted immediately.
    </Note>
  </Tab>
  <Tab title="Go Live">
    The **Go Live** action publishes the current **Test** version of a workflow to the **Live** environment, making the latest approved configuration available for production use.

    You can go live from the **More Options** menu (**⋮**) on the workflow list, or from the **GO LIVE** button in the builder. In both cases, click **CONFIRM** in the **Go Live Confirmation** window.

    ![](/images/workflow-go-live-confirmation.png)

    <Note>
    If approval requests are enabled, going live is sent as an approval request. See the **Request approval** tab. Otherwise, the workflow goes live right away.
    </Note>

    After publishing, it is recommended to open **View Details**, switch to the **Live** environment, and confirm that:

    - The expected changes are present.
    - The **Last Updated** timestamp reflects the recent publication.

    Performing this verification helps ensure that the correct version has been deployed successfully.
  </Tab>
  <Tab title="Request approval">
    If your workspace has **Approval** turned on in security settings, clicking **GO LIVE** does not publish the workflow right away. It creates an approval request instead, and the workflow goes live only after it is approved.

    ![](/images/workflow-request-approval.gif)

    <Steps>
      <Step title="Click GO LIVE">
        In the workflow builder, click **GO LIVE**, or select **Go Live** from the **More Options** menu (**⋮**). The **Request Approval** window opens.
      </Step>
      <Step title="Choose approvers">
        Select one or more approvers from the **Select Approvers** dropdown.
      </Step>
      <Step title="Add a message and choose how to publish">
        In **Write a Message**, add a short note on why you are requesting approval.

        - Select **Go live on approval** to publish the workflow automatically once it is approved.
        - Leave it unselected if you want to publish it yourself after approval.
      </Step>
      <Step title="Send the request">
        Click **REQUEST**. The pending request shows at the top of the workflow, along with how many approvals are needed.
      </Step>
      <Step title="Cancel the request (optional)">
        To withdraw the request, click **Cancel Request**, then click **Confirm**.
      </Step>
    </Steps>

    Once the request is approved, the workflow goes live automatically if **Go live on approval** was selected. If not, click **GO LIVE** to publish it.

    <Note>
    For how approvers review and respond to requests, see [Approval Request](/approval-request).
    </Note>
  </Tab>
  <Tab title="View Details">
    The **View Details** page displays the modules and dependencies used by a workflow. It lists the resources that the workflow depends on, such as **Notification Events** and **Allowlist URLs**, helping you understand which workspace components are associated with the workflow before making changes or publishing updates.

    This page is particularly useful for identifying workflow dependencies, reviewing version information, and comparing the **Test** and **Live** versions before deployment.

    **Information displayed**

    | Field | Description |
    |-------|-------------|
    | **Name** | Displays the workflow name. |
    | **Group Tag** | Identifies the group to which the workflow belongs, such as *Customer Journey* or *Internal Automation*. |
    | **Environment** | Indicates whether the displayed information relates to the **Test** or **Live** version of the workflow. |
    | **Last Updated** | Shows when the selected environment was most recently modified, helping identify the latest published or draft version. |
    | **Depends On** | Lists the resources referenced by the workflow, such as notification events, templates, components, Omni-Channel routes, API integrations, or external services used within the workflow. |
    | **Used In** | Lists the resources that reference the workflow, where applicable, allowing you to assess the impact of modifying or deleting it. |

    **Environment selection**

    The environment selector allows you to switch between the two available versions of a workflow without leaving the details page.

    - **Test** displays the draft version used for development, testing, and validation before publication.
    - **Live** displays the version currently available to end users.
  </Tab>
  <Tab title="Copy to another workspace">
    The **Copy to another workspace** action lets you copy a workflow from the current workspace to another workspace. This is useful when you want to reuse an existing workflow across multiple workspaces without recreating it manually.

    **Workflow versioning during copy**

    When a workflow is copied to another workspace, versioning is handled automatically.

    ![](/images/workflow-versions.png)

    - If the workflow does **not** exist in the destination workspace, the copied workflow is created as **Version 1 (Test)**.
    - If the workflow **already exists** in the destination workspace, the copied workflow is created as a new standalone version (for example, **v2**). You can then review the new version and either save it as the current **Test** version or publish it as the new **Live** version.

    For example, if the version in the destination workspace is `v1 (Test)`, the copy creates `v2`. Select `v2` from the version dropdown beside the workflow name and click **SAVE** to make it `v2 (Test)`, or click **GO LIVE** to make it `v2 (Live)`.

    This approach prevents existing versions in the destination workspace from being overwritten while giving you control over when to promote the copied version.

    **Prerequisites**

    Before copying a workflow to another workspace, ensure that all dependent resources used by the workflow are already available in the destination workspace. This includes:

    - Notification Events referenced by the workflow.
    - Allowlist URLs required by the workflow.
    - Any other workflow dependencies or referenced resources that are specific to the source workspace.

    <Warning>
    If the required dependencies are not present in the destination workspace, recreate or migrate them before copying the workflow to ensure it functions correctly after the transfer.
    </Warning>
  </Tab>
</Tabs>

## Access and Settings

<Tabs>
  <Tab title="Workflow URL">
    Every workflow has a URL. Other systems, such as a payment gateway or your backend, call this URL to start the workflow. Open it from **Workflow URL** in the **More Options** menu (**⋮**), or from the Workflow URL icon in the builder.

    ![](/images/workflow-url.gif)

    The **Workflow URL** window lets you:

    - Switch between the **LIVE** and **TEST** URL.
    - Choose how callers sign in, with **BASIC AUTH** or **TOKEN AUTH**.
    - Copy the URL with the copy icon.
    - Set who can call the workflow with the **Restricted** toggle.

    Click **SAVE CHANGES** to keep your changes.

    ![](/images/workflow-url.png)

    **Authentication methods**

    ![](/images/workflow-url-auth-options.png)

    | Method | When to use it |
    |--------|----------------|
    | **BASIC AUTH** | The URL carries your Fyno account details, so callers can use it as is. |
    | **TOKEN AUTH** | The URL uses a workflow token instead. You can set your own token in the **Customize Token** tab. |

    <Warning>
    Treat the Workflow URL like a password. Anyone who has it can start the workflow while access is public.
    </Warning>

    **Access level**

    By default, the access level of a workflow is public, so it can be called with either authentication method above. Turn on **Restricted** to allow the workflow to run only with your Fyno API Key.

    ![](/images/workflow-restricted-access.png)

    <Tip>
    Keep the workflow public while you build and test it, then switch it to **Restricted** once it is ready.
    </Tip>
  </Tab>
  <Tab title="Customize Token">
    If you call your workflow with **TOKEN AUTH**, you can replace its token with your own value.

    ![](/images/workflow-customize-token.gif)

    1. Open **Customize Token** from the **More Options** menu (**⋮**), or click the Customize Token icon in the builder.
    2. Enter the new value in **Enter new token value** and again in **Confirm new token value**.
    3. Click **UPDATE TOKEN**.
    4. Open **Workflow URL** and copy the new URL. Update it wherever the workflow is called.

    ![](/images/workflow-update-token.png)

    <Note>
    The URL changes when you update the token, so make sure to copy the new URL.
    </Note>
  </Tab>
  <Tab title="Change logs">
    To view the history of all the modifications made to a workflow, you can utilize the change logs feature.

    To do so, open the workflow and click the history icon at the top right of the builder, next to the **Created** or **Updated** details, as shown in the image below.

    ![](/images/workflow-builder-header.png)

    The **Change Logs** panel opens with the latest change at the top. It shows the following details:

    - Who updated it
    - Which version was updated, and what happened to it, for example **Updated (v3)** or **Went live with (v2)**
    - At what date & time it was updated

    ![](/images/workflow-change-logs.png)
  </Tab>
</Tabs>
