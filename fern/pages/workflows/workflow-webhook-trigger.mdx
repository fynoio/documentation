A Webhook trigger starts your workflow whenever another system, such as a payment gateway or your backend, calls the Workflow URL. The data it sends becomes available to every step of the workflow.

## Prerequisites

- Ensure relevant notification events which will be configured as part of Workflow are created.
- Make sure you have the sample payload which will be triggered via webhook.
- Ensure at least 1 allowlist API is configured if you want to receive delivery reports.

## How to configure a Webhook

Here is the setup at a glance.

![](/images/webhook-setup.gif)

<Steps>
  <Step title="Create the workflow">
    Navigate to **Workflows** from the left navigation panel. If you have already created a few workflows, you can see them in card view.

    Click **CREATE**, enter a name and click **SUBMIT**. The workflow canvas opens with the list of triggers.
  </Step>
  <Step title="Select the Webhook trigger">
    Select **WEBHOOK** from the triggers. The **Webhook** panel opens on the right. To pick a different trigger, click **CHANGE TRIGGER**.

    ![](/images/webhook-trigger.png)
  </Step>
  <Step title="Choose the HTTP Method">
    Under **HTTP Method\***, select the method which will call the workflow.

    - **GET**: trigger this workflow with a GET request and optional query parameters.
    - **POST**: trigger this workflow with a POST request and a payload with the appropriate content type.

    ![](/images/webhook-http-method.png)
  </Step>
  <Step title="Choose the Content Type">
    If you select POST, then you need to select the content type of the payload under **Content Type\***.

    | Content Type | What it means |
    |--------------|---------------|
    | **None** | No payload will be sent when triggering the workflow. |
    | **JSON** | Content type will be set to `application/json`. |
    | **Form Data** | Content type will be set to `multipart/form-data`. |
    | **URL Encoded Form** | Content type will be set to `application/x-www-form-urlencoded`. |
    | **XML** | Content type will be set to `application/xml`. |
    | **Text** | Content type will be set to `text/plain`. |

    ![](/images/webhook-content-type.png)
  </Step>
  <Step title="Add a Sample Payload">
    If you have selected JSON, Form Data or URL Encoded Form, then you need to add a sample payload as shown below.

    ![](/images/4365960-add_sample_payload.png)

    Once you click **Add Sample Payload**, a page will open where you can enter the sample payload.

    ![](/images/workflow_webhook_sample_payload.png)
  </Step>
  <Step title="Add Query Parameters (optional)">
    Expand **Query Parameters (Optional)** if the workflow URL will include query parameters. These are primarily used with GET requests and are appended to the URL path after a `?` character, for example `/users?page=1&per_page=20`.

    Enter each one in **Enter Key** and **Enter Value**. Click **ADD ANOTHER** to add more.

    ![](/images/webhook-query-parameters.png)
  </Step>
  <Step title="Add Headers (optional)">
    Expand **Headers (Optional)** if you want to send any HTTP headers when running the workflow. Headers give the server extra information to process the request, and each has a key and a value, for example `Cache-Control: no-store, no-cache, must-revalidate`.

    Enter them in **JSON** or switch to **FORM** to add them field by field.

    ![](/images/webhook-headers.png)
  </Step>
  <Step title="Simplify the payload (optional)">
    Using complex payloads for placeholder mapping can be challenging, and using the same payload variable again and again in conditions is cumbersome. **Simplify** lets you create your own variables, map payload fields to them, build expressions from payload fields, and use these variables throughout the Workflow. Click **Simplify** at the top right.

    - When directly mapping payload data, you can link, for example, `acquirer_data.authentication_reference_number` to the variable `ref_no`.
    - If you're using Handlebars (HBS), use the payload data as `$input.body.status` to map it to a variable like `payment_status`. Using just `payload.status` will result in an error. To know more about Handlebars, refer to our [documentation](./templates-handlebars).

    ![](/images/workflow_simplify_mapper.png)

    <Info>
    There is no restriction on the number of mapper variables created. All mapper variable names need to be unique.
    </Info>

    <Warning>
    Mapper variable name must not be any of the following: `body`, `headers`, `formdata`, `query` or `method`.
    </Warning>
  </Step>
  <Step title="Save">
    Click **SAVE**. Once the trigger is saved, you can add action and condition blocks after it.
  </Step>
</Steps>

## How does Workflow Work?

Let's illustrate this with our payment gateway example used by the ABC company. When ABC creates the Workflow in Fyno, they will configure their payment gateway to call the Workflow URL anytime a payment is processed.

![](/images/webhook-example.gif)

Let's assume that the response sent by the payment gateway for a successful payment is the below JSON.

```json title="Payload for successful payment" wordWrap
{
  "payment_id": "P1",
  "order_id": "O121",
  "payment_status": "success",
  "customer_details": {
    "name": "John Doe",
    "email": "john@email.com"
  },
  "payment_details": {
    "method": "card",
    "card_number": "XXXXXXXXX1234"
  }
}
```

When a payment succeeds, the gateway will invoke the Workflow URL by including the above response as a payload.

The details that we configure in the trigger step should reflect the details used by the source calling the Workflow. So in our example, if the gateway is invoking the Webhook/Workflow URL as a `POST` request, this is how ABC will configure the trigger:

| Setting | Value | Why |
|---------|-------|-----|
| **HTTP Method** | `POST` | The gateway calls the URL with a POST request. |
| **Query Parameters** | Empty | The gateway does not add any query strings to the URL. |
| **Headers** | Empty | The gateway does not pass any headers. |
| **Content Type** | JSON | The payload is of type JSON. |
| **Sample Payload** | The JSON above | The payment success payload from the gateway. |

<Note>
The data configured in the trigger step is just a sample, used to build the rest of the Workflow. If the payment gateway adds a new attribute to the response, the Workflow will still run as expected with the old payload. However, if you need to use this new attribute in the Workflow, you must update the trigger step with the new payload.
</Note>

Once the **Trigger** has been set up and saved, you can drag and drop any action block or condition block.

![](/images/workflow_controls_actions.png)

## Action

An **Action** block can be added immediately after the trigger or based on the outcome of a **Condition**.

<Tabs>
  <Tab title="Notification Event">
    **Notification Event** refers to the notification events created within Fyno and can be called as an action for the payload that was added in the previous step of the workflow.

    When you add a **Notification Event**, set up the following:

    - **Notification Event:** Select a relevant notification event from the dropdown, specific to this trigger.
    - **Map Data:** On selecting the notification event, you will see the mapping details. For the notification event you have selected, you need to specify details from the payload received from the trigger.
      - **Distinct Id:** If you are using Fyno's user profile, select the value for Distinct Id from the payload or a custom variable created using **Simplify**.
      - **Channels:** All the channels configured in the template linked to the selected notification event appear here. If you are not using Fyno's user profile, map the channel level destinations from the payload data or custom variables created with **Simplify**. In this example, the template linked to the notification event `sms-test-2` has only SMS as the channel, which is why you see SMS under Map Data.

      ![](/images/d1460ba-Event_Mapping.png)

    - **Data:** You will see all the fields that you have specified as **Placeholders** (dynamic values) in the template linked to the notification event. If you do not see this field, there are no placeholders in the template.

      ![](/images/6caa7b5-event_maping_data.png)

    - **Additional Data (optional):** Additional data in the form of a JSON payload. A typical use case is when you did not add placeholders manually during template creation. For instance, if your template contains `Hi {{name}}` but you did not add `name` as a placeholder, Fyno still identifies `name` as a placeholder since it uses the `{{ }}` syntax. Add `name` as the key here and select a value from the dropdown.
  </Tab>
  <Tab title="API">
    Fyno's Workflow enables you to call external APIs and run the next part of the workflow based on the response received. This makes workflows extremely powerful and flexible.

    The first step to calling an external API in a Workflow is to allowlist the API endpoint:

    1. Navigate to the [Allowlist URL page](https://app.fyno.io/webhooks).
    2. Add and verify the URL or endpoint.

    When you add the **API** node, you'll see the following:

    ![](/images/workflow_call_api_request.png)

    - **Allowlist URL Name:** Select a URL from the allowlist.
    - **Cache response of this API? (optional):** Fyno caches the API response for a set time based on the key value. The workflow uses the cached response until the time runs out or the key value changes, so it doesn't call the API again for nothing.
      - **Cache Key:** Select the key value you want to cache.
      - **Time & Unit:** Select a duration between 1 minute and 1 day.

      ![](/images/workflow_API_response_cache.png)

    - **Method:** GET or POST.
    - **Content Type:** If you select POST, choose the content type of the payload. The options are the same as for the [Webhook trigger](#how-to-configure-a-webhook).
    - **Sample Payload:** If you have selected JSON, Form Data or URL Encoded Form, add a sample payload. Click **Add Payload**, then either:
      1. Paste the payload in the JSON window, or
      2. Select **Use sections of the sample payload submitted during trigger configuration** and pick one of the sections.

      ![](/images/workflow_call_api.png)

      ![](/images/workflow_api_response_content.png)

    - **Query Parameters (optional):** Primarily used with GET requests, for example `/users?page=1&per_page=20`.
    - **Headers (optional):** For example, `Cache-Control: no-store, no-cache, must-revalidate`.
    - **Simplify:** Works the same way as in the trigger. See [Simplify the payload](#how-to-configure-a-webhook).

    <Tip title="The response of an API call can be used to configure notification events.">
    For instance, if your API call returns a key `email` with the email address you want to use in the next notification event, use a custom variable with the value `{{$http_response.data.email}}` to configure the email in the notification event.
    </Tip>
  </Tab>
</Tabs>

## Condition

The **Condition** feature within Workflow lets you add all the logic you need to handle different situations within a single workflow. Conditions can be written for the parameters in the payload received from the trigger, and help direct the flow based on them.

![](/images/0f42772-workflow_condition.png)

Choose what the condition should check:

<Tabs>
  <Tab title="Variable">
    - **Variable:** Select the variable you want to base the condition on.
    - **Operator:** Select an operator from the [list below](#supported-operators).
    - **Value:** Specify the value the If/Else condition will check against.
  </Tab>
  <Tab title="HTTP Status Code">
    Select this option to create a condition based on the HTTP status code of an **API** action. The status code can be success (`200`, `201`, `2xx` etc.) or failure (`4xx` or `5xx`).

    - **Operator:** Select an operator from the [list below](#supported-operators).
    - **Value:** Specify the status code the If/Else condition will check against.
  </Tab>
  <Tab title="HTTP Response">
    Select this option to create a condition based on the HTTP response of an **API** action. The response can be a string or a JSON key.

    - **HTTP Response:** Specify the key from the API response. If the response looks like `{status: "ok"}`, enter `status`. If the response is nested like `{status: {response: "ok"}}`, enter `status.response`.
    - **Operator:** Select an operator from the [list below](#supported-operators).
    - **Custom Value:** Specify the value the If/Else condition will check against.
  </Tab>
</Tabs>

### Supported operators

The **Operator** field supports the following:

- Equals
- Not Equals
- Starts With
- Ends With
- Contains
- In
- Greater Than
- Less Than
- Greater than or Equal
- Less than or Equal
- Is
- Is Empty
- nin
- is boolean

## Workflow URL

The URL is auto-generated when you create the workflow. You need to use this URL to invoke the Workflow. Once you save or go live with your workflow, you will see a popup as shown below.

![](/images/workflow_url_copy.png)

You can also open the Workflow URL by clicking the Workflow URL icon at the top right, next to the **GO LIVE** button.

We provide URLs for both **TEST** and **LIVE**. Copy both URLs and configure them in your system or any third party tool where the webhook will be triggered. For more on this window, see [Access and Settings](/workflows#access-and-settings) on the Workflows page.

<Tabs>
  <Tab title="Public">
    If you are using a public URL, you can select one of these 2 options:

    - **BASIC AUTH:** The URL consists of your workspace ID and the token which Fyno uses for authentication.
    - **TOKEN AUTH:** The URL includes a query parameter `token=<Fyno_generated_token>`.

    ![](/images/workflow_basic_url.png)

    <Info>
    Workflows are public by default. If you turn on **Restricted** after the workflow is created and save it, you must use the Restricted URLs (Live and Test) when running the workflow.
    </Info>
  </Tab>
  <Tab title="Restricted">
    To use restricted access, turn on the **Restricted** toggle. You can select one of these 2 options:

    - **Bearer Token:** Pass your Fyno API Key as a bearer token in the authorization header: `{'Authorization': 'Bearer <YOUR_FYNO_API_KEY>'}`.
    - **Basic Auth:** The URL consists of your workspace ID and API Key, which Fyno uses for authentication. Example: `https://<WORKSPACE_ID>:<API_KEY>@api.fyno.io/v1/automation/XXXXXXX`

    ![](/images/workflow_restricted_url.png)
  </Tab>
</Tabs>

<Tip title='You can update the token using the "Customize Token" option in the workflow header.'>
Since the workflow URL can be called from anywhere, it is a good idea to update the token if you feel it has been compromised. Always remember to update the workflow URL (with the new token) wherever the workflow is called.
</Tip>

## Request Approval to Go Live

If your workspace has **Approval** turned on, clicking **GO LIVE** creates an approval request instead of publishing the workflow right away.

![](/images/workflow-request-approval.gif)

<Steps>
  <Step>Click **GO LIVE** to open the **Request Approval** window.</Step>
  <Step>Select one or more approvers from **Select Approvers**.</Step>
  <Step>Add a note in **Write a Message**. Select **Go live on approval** to publish automatically once approved.</Step>
  <Step>Click **REQUEST**.</Step>
</Steps>

You can read more about it on the [Approval Request](/approval-request) page.
